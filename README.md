# Wimbledon 2026: Random Forest Win Probability Model

A random forest that estimates match win probabilities for the 2026 Wimbledon gentlemen's singles draw, trained on ATP match data from 2015 to 2026, together with a Monte Carlo simulation of the bracket.

The model is validated three ways, in increasing order of how much the result should be believed:

1. Cross-validation against itself, trained on all surfaces and scored on Wimbledon matches only.
2. A strictly chronological walk-forward backtest against devigged bookmaker odds on seven past Wimbledons. This is the headline number, because the market is a real adversary rather than a held-out slice of the same data.
3. A post-mortem against the 2026 tournament itself, which finished on 12 July 2026 and so is now falsifiable.

Every number below is written by a script into `results/` and spliced into this file by `build_readme.py`. Nothing here is typed by hand.

The market wins, which is the expected result and the honest one to lead with. What matters is the size of the gap and where it sits. A gap concentrated in early rounds against qualifiers is a different proposition from one spread evenly, because the former suggests the model is losing exactly where the market has the least information and the most margin. The round breakdown above is the first place to look for that.

Two caveats on reading this as a trading result. Beating the market on log-loss is necessary but not sufficient: a trade also has to clear the fee, and prediction-market venues such as Kalshi and Polymarket charge enough to erase a thin edge. And a paired bootstrap interval that straddles zero means the gap is not distinguishable from noise at this sample size, whichever direction it points.

## Data

ATP match-level data from 2015 to 2026 across all surfaces, via [tennisabstract.com](https://tennisabstract.com). Each match with a valid date and both player rankings contributes two training rows, one from each player's perspective, so the label is balanced by construction and the model cannot learn a positional prior on whichever player happens to be listed first. Exact counts appear in the [model detail](#model-detail) section.

Features for a given match are built from `Player_Stats` state as it exists *before* `update_after_match` is called on that match. No row can see its own outcome, and no career statistic includes matches that had not yet been played.

## Model choice: why random forest?

Three properties of tennis-match data rule out a plain logistic regression and make a neural network impractical, while a random forest handles both:

- **Non-linearity.** Several features have diminishing or plateauing effects rather than linear ones. For example, the gap between a bad serve and a good serve matters more than the gap between a good serve and a great one. `ace_rate`, `grass_serve_quality`, and `peak_rank` all show this pattern.
- **Multicollinearity.** The win-rate features (`grass_win_rate`, `ytd_win_rate`, `top10_win_rate`, `peak_wimb_rate`) and the serve features (`grass_serve_quality`, `ace_rate`, `second_serve_won_pct`) are correlated by construction (r = 0.5 to 0.7 between related pairs; `rank_diff` and `wimb_formula_diff` are r = -0.83). A regression's coefficients would be unstable under this; a tree ensemble is unaffected.

![Correlation heatmap for features](./correlation_heatmap.png)

- **Non-independence of observations.** A player's form and fatigue carry from match to match within a tournament, so the assumption behind standard regression inference does not hold cleanly here either.

A neural network would in principle handle the non-linearity too, but grass is the shortest ATP season by a wide margin, roughly 10% of tour matches, so the effective sample size on the grass-specific features is too small to train. A neural network would also lose the interpretability that is useful with these features.

### Hyperparameters

| Parameter | Value | Rationale |
|---|---|---|
| `n_estimators` | 1000 | More trees reduce the variance of the ensemble's averaged class-probability estimate. |
| `max_depth` | 15 | 25 features with paired (p1/p2) structure need enough depth to capture interaction effects between them. |
| `min_samples_leaf` | 25 | Regularizes against `max_depth=15` by requiring historical support behind every split. |
| `criterion` | `log_loss` | Penalizes confident wrong predictions more than Gini does, which matters because the output used downstream is the probability itself, not just the argmax class. |

## Features

| Feature | Description |
|---|---|
| `rank_diff` | Log-difference of ATP rank. A move from 1 to 50 is not equivalent to 50 to 100, so a raw rank difference would be misleading. |
| `peak_rank` | Player's best-ever ATP ranking. |
| `grass_win_rate` | Career win rate restricted to grass-court matches. |
| `peak_wimb_rate` | Best single-year win rate the player has posted at Wimbledon itself. |
| `ytd_win_rate` | Win rate in the current season, as a form signal. |
| `top10_win_rate` | Win rate specifically against top-10 opponents, a proxy for upset and deep-run potential. |
| `ace_rate`, `first_serve_pct`, `second_serve_won_pct` | Serve statistics, grass-restricted. |
| `grass_serve_quality` | Share of service points won, grass-restricted. Does not yet account for serve speed. |
| `wimb_formula_diff` | Proxy for Wimbledon's former seeding formula, ATP rank blended with a grass-specific rating, reconstructed from rolling grass results to test whether it would still carry predictive value if reinstated. |
| `is_grass_match`, `is_clay_match`, `is_best_of_5` | Match context. The model trains on all surfaces, so it needs to know which surface it is looking at. Without these it cannot distinguish a clay match from a grass one while the grass-specific features above sit median-imputed. |
| `grass_n` | `log1p(grass matches played)`, per player. Encodes both whether a player has any grass history and how much, so the forest can discount an imputed median rather than treating it as an observed value. |

## Model detail

Trained on all surfaces; cross-validated on the Wimbledon slice only.

`GroupKFold` splits the full frame on `match_id`, so each training fold keeps the whole all-surface sample minus the held-out matches, and a match's winner-row and loser-row can never straddle a split. The test fold is then restricted to its Wimbledon rows before scoring. Median imputation is fit inside each training fold rather than on the full frame, so held-out rows contribute nothing to their own fill values.

A one-parameter logistic on `rank_diff` alone is reported alongside as a floor. Any model that does not clear "pick the higher-ranked player" is not doing work.

**This number is optimistic and should not be quoted as live performance.** `GroupKFold` is not time-aware: it shuffles matches across seasons, so a fold can train on 2025 and predict 2016. The walk-forward backtest at the top of this README is the number that respects chronology, and the gap between the two is itself informative.

## Validating against the market

Cross-validation only checks the model against itself. For anything trading-adjacent, the relevant question is whether the model prices matches better than the people already pricing them.

- Historical Wimbledon odds come from `data/odds/{year}.xlsx` (tennis-data.co.uk), converted from decimal odds into a fair no-vig probability, since raw odds imply a total above 100% once the bookmaker's margin is included. Pinnacle is preferred as the sharpest book, with Bet365 and the market average as fallbacks.
- The model is trained once on data strictly before the earliest backtest year, then walked forward chronologically match by match, so no future information reaches any prediction.
- Both model and market are scored with log-loss and Brier on the same matches, with a paired bootstrap interval on the difference.

Two details that determine whether the comparison means anything. First, **join coverage is reported explicitly**. Reconciling tennis-data's `Del Potro J.` against Sackmann's `Juan Martin del Potro` is where this silently goes wrong: a naive last-token split drops every compound surname (del Potro, de Minaur, Bautista Agut, Davidovich Fokina, van de Zandschulp, Carreno Busta), which is a non-random slice of the field. The resolver here generates every plausible surname split and matches the longest, and any residual failures are printed rather than skipped. Second, rows are stored winner-first, so **match orientation is randomised** with a fixed seed before scoring; otherwise every label is 1 and the evaluation is degenerate.

## Live tournament updating

`wimbledon_rf.py` produces a single static snapshot from pre-tournament information. `resimulate.py` collapses the bracket to survivors as rounds complete and resimulates forward, which is the form a live position would need.

The fitted model genuinely is left alone between rounds: it is trained once, cached to `data/model.joblib`, and reloaded on later runs. Pass `--refit` to retrain deliberately. Refitting a 1000-tree forest on a handful of new rows between rounds would be noise-chasing, not learning.

What this does **not** do is update player form from the tournament in progress. `Player_Stats` is built from the historical CSV only, so a player who has just won three matches carries the same features into round four that he had on day one. The update is bracket collapse, not information update. Feeding in-tournament results into the accumulators is listed under Going forward.

State is persisted to `data/tournament_state.json`, so each run needs only that round's results. Results files are validated against the draw before anything is written: unknown names, already-eliminated players and duplicate losers are rejected, and a partially applied round is caught by a power-of-two check on the survivor count. A failed run leaves state on disk unchanged.

## Limitations

- **No time decay on historical rates.** `grass_win_rate`, `top10_win_rate` and the rest are unweighted career rates, so a win from 2015 counts identically to one from last month, despite form and injury cycles moving faster than that.
- **Uncalibrated probabilities.** Random forests compress probabilities toward 0.5 relative to true frequencies, particularly with a smoothing parameter like `min_samples_leaf=25`. No calibration layer has been fitted. The post-mortem calibration table shows the size of the problem on real outcomes; until it is corrected, these probabilities are better trusted as a ranking than as frequencies.
- **Imperfect antisymmetry.** The forest trains on both orderings but does not learn exact antisymmetry, so `P(a beats b)` and `1 - P(b beats a)` disagree slightly. The simulation averages both orderings, which makes the matrix exactly antisymmetric and removes what was previously a dependence on alphabetical name order. The mean violation is reported above as a coherence check.
- **`wimb_formula_diff` overlaps heavily with rank.** At r = -0.83 with `rank_diff`, its base term dominates for highly ranked players, so much of its importance is rank arriving under a second name. Whether the Wimbledon seeding formula carries signal *beyond* rank is not yet answered; that requires orthogonalising the feature against `rank_diff` and testing the residual.
- **Random-fold rather than time-respecting cross-validation.** See the caveat under Model detail.
- **Missing shot-level data.** Serve speed, rally shot placement, and groundstroke pace are not available at the resolution this would need.

## Going forward

- Fit a calibration layer and report a reliability diagram before and after, then rerun the market backtest to see how much of the gap it closes.
- Orthogonalise `wimb_formula_diff` against `rank_diff` and test whether the residual carries any importance. This is the actual research question the feature was built to answer.
- Add exponential time decay to the historical rate features.
- Feed in-tournament results into `Player_Stats` so `resimulate.py` performs an information update rather than a bracket collapse.
- Extend the backtest into a sized signal against Kalshi or sportsbook markets, sizing off the model-versus-market edge net of fees rather than reporting probabilities alone, and track which trades win and lose.

## Reproducing

```bash
pip install -r requirements.txt
python fetch_data.py
python wimbledon_rf.py
python odds_backtest.py --years 2018 2019 2021 2022 2023 2024 2025
python postmortem.py
python build_readme.py
```

Every script takes `--seed` and defaults to 42. Model fitting, the bracket Monte Carlo, the bootstrap, and the orientation randomisation are all seeded, so repeated runs are identical. `python build_readme.py --check` exits non-zero if this README has drifted from `results/`.
